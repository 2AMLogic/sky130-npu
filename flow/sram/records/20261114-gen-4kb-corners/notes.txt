Slow- and fast-corner Liberty generation attempt for the pinned 4 KB macro
sky130_sram_4kbyte_1rw1r_32x1024_8 (issue #153, spec gaps G1 and G2).

Run at main f79ce01 through the pinned openram-toolchain (flow/sram/setup.sh),
reusing an existing scratch dir, ONE local OpenRAM job, 1727 s, exit 0. Not a
grid, not parallelized, nothing sent to the batch fleet. See run-record.txt for
commits, hashes and the accepted corner list, and
gen_4kb_1rw1r_32x1024_corners.log.tail for the tool log (host paths scrubbed).


1. OUTCOME: both corners WERE produced, at the exact PVT points section 7 names
-------------------------------------------------------------------------------
The toolchain accepted the corner list verbatim:

    characterize_corners: [('TT', 1.8, 25), ('SS', 1.6, 100), ('FF', 1.95, -40)]

and wrote three Liberty files:

    sky130_sram_4kbyte_1rw1r_32x1024_8_TT_1p8V_25C.lib    (baseline)
    sky130_sram_4kbyte_1rw1r_32x1024_8_SS_1p6V_100C.lib   (new)
    sky130_sram_4kbyte_1rw1r_32x1024_8_FF_1p95V_-40C.lib  (new)

So the answer to "can the pinned generator produce these corners at all" is
yes. The route is one config variable, use_specified_corners; nothing was
patched in the pinned tree.

The run also re-derived the TT view BYTE-IDENTICALLY to the already-pinned file
(sha256 6331177b...; `cmp` reports no difference), and the Verilog hash
(214e22b8...) also matches the pinned file. That is the same-run baseline the
corner numbers below are compared against, and it shows the corner machinery
does not perturb the nominal view. LEF and GDS hashes differ from the 2026-11-07
run, as the existing views_note already records for those two views.

delay table, the transition table, min_period, min_pulse_width and dynamic
power all differ. The per-pin setup/hold constraint tables do NOT -- they are
bit-identical in all three views. Both halves are inventoried in section 4;
the table below gives the representative numbers.

3. BUT THE SLOW CORNER IS NUMERICALLY DEGENERATE: a pole 0.94 C away
---------------------------------------------------------------------
Read in the pinned tree at compiler/base/hierarchy_spice.py:610-651, an
analytical "corner" is the TT number multiplied by three algebraic factors:

    apply_corners_analytically()  delay * proc_mult * volt_mult * temp_mult
    get_process_delay_factor()    'S'->1.1, 'T'->1.0, 'F'->0.9 (max over letters)
    get_voltage_delay_factor()    nom_supply_voltage / vdd
    get_temp_delay_factor()       (nom_supply - nom_threshold)
                                  / (nom_supply - vthresh), with
                                  vthresh = nom_threshold + 2*(0.008625*(T - 25))

With the sky130 tech constants (nom_supply 1.8 V, nom_threshold 0.49 V,
nom_temperature 25 C, technology/sky130/tech/tech_configs/tech_cypress_cell.py)
that closed form predicts the observed numbers to rounding:

    SS 1.60 V 100 C : 1.1 * 1.125 * 80.615 = 99.76x  (observed 99.62-99.77x)
    FF 1.95 V -40 C : 0.9 * 0.923 * 0.539  =  0.448x (observed 0.446-0.447x)

The slow corner's factor is almost entirely temperature: 80.6x on its own. That
is because its denominator (nom_supply - vthresh) = 1.8 - 1.78375 = 0.01625 V is
nearly zero. The formula has a POLE at T = 100.94 C:

    T =  99 C -> temp factor    39.10
    T = 100 C -> temp factor    80.62     <- the corner section 7 names
    T = 101 C -> temp factor -1310.00     <- past the pole, NEGATIVE delay

The spec's ss_100C_1v60 therefore sits 0.94 C below a division by zero, on the
steepest part of a curve that is unbounded and then changes sign. Its
min_period 177.497 ns (5.63 MHz) is an artifact of that linearised threshold
extrapolation, NOT a slow-corner timing estimate. Reporting the 50 MHz target
against it would be meaningless in either direction: it does not show the
target missed, because the number is not a physical delay.

The fast corner's 0.448x is numerically plausible, but it comes from the same
three-factor fudge and the same analytical model.


4. WHAT DOES NOT TRACK THE CORNER: LEAKAGE, max_transition, AND EVERY
   PER-PIN SETUP/HOLD CONSTRAINT
----------------------------------------------------------------------
cell_leakage_power is bit-identical (0.035146 mW) in all three views. Leakage is
the single most temperature-sensitive quantity in a real library; a hot slow
corner with exactly the nominal leakage is not a leakage view. max_transition is
likewise the 0.5 default at every corner, not a derived limit.

The same is true of every input timing CONSTRAINT, which matters more, because
those are the load-bearing numbers of a hold view. Pairing all 44 values(...)
timing tables in each view by pin + timing_type + table name, and diffing the
three views against each other:

  28 of 44 tables are BIT-IDENTICAL at TT, SS 1.60V/100C and FF 1.95V/-40C
    7 constrained input pins x {setup_rising, hold_rising}
                             x {rise_constraint, fall_constraint}
    pins: din0[31:0], addr0[9:0], wmask0[3:0], csb0, web0, addr1[9:0], csb1
    setup_rising :  0.103 ns   hold_rising : -0.056 ns
    every one of the nine grid points, in all three views

  16 of 44 tables MOVE
    dout0[31:0], dout1[31:0] x {cell_rise, cell_fall,
                                rise_transition, fall_transition}   (8 tables)
    clk0, clk1 x {min_pulse_width, minimum_period}
               x {rise_constraint, fall_constraint}                 (8 tables)

So the ONLY constraints that move with the corner are clk0/clk1's
min_pulse_width and minimum_period -- which are clock-waveform limits derived
from the delay factor, not per-pin setup or hold checks. Not one of the 28
per-pin setup/hold tables was derated at all; they are TT's numbers verbatim,
wearing an SS or FF label.

Consequence, stated for whoever reads these views next: NEITHER NEW VIEW
SUPPLIES ANY CORNER-SPECIFIC SETUP OR HOLD INFORMATION. This bites the fast
view hardest. ff_n40C_1v95 is the HOLD signoff corner (gap G2), and a hold
view's load-bearing numbers are exactly those per-pin hold constraints. The
slow view's degeneracy is self-announcing -- 177.497 ns is absurd on sight --
but -0.056 ns hold under an FF label looks entirely reasonable and is not. A
later STA step that reads the FF view, decides the delay tables are too
approximate to trust but the constraints look fine, and reports hold closed at
ff_n40C_1v95, would be reporting TT hold constraints. Both lock caveats say so.

Dynamic power moves the wrong way: it is 112x LOWER at the slow-hot corner than
at TT, because the model divides power by the delay factor (calc_dynamic_power,
hierarchy_spice.py:658-670: "Increased delay -> slower freq. -> less power").

(The absolute dynamic power figure, 2.0e+11 mW at TT, is pre-existing nonsense
in this toolchain, not introduced here: the identical value appears in the
2026-11-07 TT record, flow/sram/records/20261107-gen-4kb-1rw1r-32x1024/stdout.tail.)


5. AN ANALYTICAL VIEW IS NOT A SPICE-CHARACTERIZED ONE
-------------------------------------------------------
Stated plainly, as the issue's fifth criterion requires: all three of these
Liberty views come from OpenRAM's analytical (Elmore) delay model with
analytical_delay at its default. No SPICE simulation of this macro was run for
any of them. An analytical view is an estimate produced by closed-form
formulas over the extracted critical path; it is NOT a SPICE-characterized
library, and the corner scaling in particular (section 3) is algebraic, not
simulated.

Consequence, recorded rather than assumed: GAPS G1 AND G2 STAY OPEN. Files now
exist at both corners and are pinned, but neither is a signoff view - both carry
usable_for_signoff: false in reuse.lock.json. Closing G1 or G2 requires SPICE
characterization of the macro, which this issue puts out of scope and which has
not been done. spec/npu.md is deliberately NOT edited by this work.

They are pinned anyway, rather than left out, so that the lock - the file an STA
step actually reads - carries the pole and the leakage finding next to the
hashes, instead of leaving a later agent to regenerate these views and use them
unaware.


6. HOW THE PVT POINTS MAP TO THE SECTION 7 CORNER NAMES
--------------------------------------------------------
The pairing is by PVT, NOT by file name. Section 7 names std-cell Liberty
corners; these macro views are named from OpenRAM's own PVT string
(compiler/characterizer/lib.py:139-146, "." replaced by "p"):

  section 7 corner   std-cell Liberty                  macro view here
  ss_100C_1v60       sky130_fd_sc_hd__ss_100C_1v60.lib ..._SS_1p6V_100C.lib
                     (setup signoff, the 50 MHz figure; gap G1)
  tt_025C_1v80       sky130_fd_sc_hd__tt_025C_1v80.lib ..._TT_1p8V_25C.lib
                     (informational)
  ff_n40C_1v95       sky130_fd_sc_hd__ff_n40C_1v95.lib ..._FF_1p95V_-40C.lib
                     (hold signoff; gap G2)

Each macro view is intended to be read with the std-cell corner on its row,
because the PVT points were chosen to match. Note 1.60 V appears in the file
name as 1p6V (Python formats 1.60 as 1.6), and the fast-corner file name
contains a literal "-40", so its path must be quoted in shell handling.

One header detail that may surprise a reader of section 3: all three views carry
process : 1.0 and nom_process : 1.0 in operating_conditions, so an STA tool sees
three OCs differing only in V and T. OpenRAM never writes the process letter
into the header, even though section 3 shows that letter (1.1 / 1.0 / 0.9) does
enter the delay product. The tables are ALREADY scaled by that factor, so this
is the harmless arrangement rather than a defect: a process value other than 1.0
in the header would double-count the same derate under a tool's k-factor
derating.

Also worth stating: 1.60 V, 1.95 V and -40 C are all OUTSIDE the sky130 tech's
own corner lists (supply_voltages [1.7, 1.8, 1.9], temperatures [0, 25, 100]).
The points are reachable only because use_specified_corners bypasses those
lists; no combination of the tech defaults produces them.


7. ROUTES THAT DO NOT WORK (checked, so the next attempt need not re-check)
----------------------------------------------------------------------------
- nominal_corner_only = False: compiler/globals.py:534 reads
  tech.spice["fet_models"], but the sky130 tech defines spice["fet_libraries"]
  and has no fet_models key -> KeyError before any SRAM is built. Confirmed by
  reading both files at the pinned commit; not executed, because the route is
  rejected anyway. Even patched it would not help: lib.py:119-130 varies one PVT
  axis at a time about nominal, so SS/FF would come out at nominal 1.8 V / 25 C.
- only_use_config_corners = True: raises UnboundLocalError. CONFIRMED
  STATICALLY (AST of the pinned compiler/characterizer/lib.py, not merely read):
  in create_corners, `nom_corner` is Stored only at line 119, inside the else
  branch, and has no Store anywhere in the only_use_config_corners branch; it is
  Loaded unconditionally at lines 132-133, after the if/else, on both paths.
  Its cross product would also characterize up to 27 corners instead of 3.
  Not executed: a 1727 s build to observe a statically certain NameError is not
  worth the compute.
- Patching the pinned OpenRAM tree: setup.sh resets the scratch tree to the
  pinned commit before hashing, so the edit is discarded by design. The two
  OpenRAM defects above belong upstream; filing them is out of scope here.

Both defects are OpenRAM's, not klayout-tools', so neither is a klt friction
item under the repo's friction protocol.


8. REPRODUCING THIS RUN
------------------------
    flow/sram/setup.sh \
      --config flow/sram/gen_4kb_1rw1r_32x1024_corners.py \
      --out-stem sky130_sram_4kbyte_1rw1r_32x1024_8 \
      --macro-config sky130_sram_4kbyte_1rw1r_32x1024_8.py \
      --record <new-id>

--config / --out-stem / --macro-config were added to setup.sh by this issue so a
named config can be run and recorded without a second near-duplicate runner. The
probe path keeps its behaviour with one cosmetic exception: its scratch output
directory is now $SCRATCH/run-out rather than $SCRATCH/probe-out, shared with
the --config path. That directory is outside the repo, rm -rf'd at the start of
each run and named only by historical *.log.tail evidence, so nothing reads the
old name -- but a reused SRAM_SCRATCH keeps a stale probe-out/ until it is
cleaned. The record directory is append-only, so a re-run needs a fresh id.

The exact overrides to the pinned config are the four the TT run already used
(use_nix, check_lvsdrc, output_path, output_name) plus exactly one addition:

    use_specified_corners = [("TT", 1.8, 25), ("SS", 1.60, 100), ("FF", 1.95, -40)]

nominal_corner_only is left at the pinned config's True on purpose: with
use_specified_corners set it is not consulted for the corner list, and leaving it
True keeps set_default_corner() on its single-element path so the unconditional
min()/max() calls at lib.py:94-99 stay well defined.

The numeric comparison in sections 2 and 4 was made by extracting
operating_conditions, every values(...) table, cell_leakage_power and
max_transition from each .lib and diffing those sets against the committed TT
view. The values(...) tables were keyed by pin + timing_type + table name so the
three views pair up table by table; that pairing is what yields the 28-identical
/ 16-moving split reported in section 4, over 44 timing tables per view.
