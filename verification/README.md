# verification

cocotb + Icarus harness and the bit-exact testbenches for `rtl/npu_top.v`,
compared byte for byte with the integer golden model (`golden/`).

## Cold start

Needs Python 3.9+ and Icarus Verilog 13.0 (CI builds tag `v13_0`; the runner
records the `iverilog -V` string in every record).

```sh
python3 -m venv .venv
.venv/bin/pip install -r verification/requirements.txt
.venv/bin/python verification/runner.py                    # ARRAY_N=8 (target)
.venv/bin/python verification/runner.py --param ARRAY_N=4   # fallback size
./verification/check_mutation.sh                            # suite must catch a 1-bit RTL error
```

Exits 0 and writes one record under `verification/records/` on success; exits
non-zero on any test failure (a failing run still writes its record). To
enforce the Icarus version: `EXPECT_ICARUS=13.0 .venv/bin/python verification/runner.py`.

The runner takes the DUT from arguments or env, so nothing needs editing in a
stamped copy:

```sh
.venv/bin/python verification/runner.py --toplevel mydut \
    --sources rtl/a.v rtl/b.v --param WIDTH=16 --test-module test_mydut
```

The defaults are `npu_top`, the `rtl/check.sh` source list, `ARRAY_N=8` and
`test_bitexact`. (`HDL_TOPLEVEL`, `HDL_SOURCES`, `HDL_PARAMS`, `TEST_MODULE`,
`TEST_DIR`, `RECORDS_DIR`, `BUILD_DIR`, `TESTCASE` (one test function),
`NPU_SEED` (random-test seed) are the env equivalents.) Parameters are also
exported to the test as environment variables.

## Layout

| Path | Role |
|---|---|
| `runner.py` | cocotb runner, Icarus, parameter-driven; writes the ledger record |
| `requirements.txt` | pinned cocotb |
| `tests/npu_bench.py` | Wishbone master, bank load/store, tiling, utilization accounting (touches only `npu_top` ports) |
| `tests/test_bitexact.py` | the four reference workloads, requantization edge vectors, K extremes, back-to-back, reset mid-run, `ERR_CODE` 1..5, constrained random |
| `check_mutation.sh` | corrupts one RTL output bit in a temp copy and passes only if the suite fails |
| `check_mutation_gl.sh` | the same negative control on a copy of the synthesized netlist (gate-level run) |
| `models/` | SRAM macro stand-in and its fidelity testbenches (sky130-specific; not stamped) |
| `golden/` | bit-exact integer golden model and workload generator (spec sections 3, 4, 8) |
| `workloads/` | committed vectors for the four reference workloads, regenerated by `golden/workloads.py` |
| `tests/test_golden.py` | golden-model unit tests (`python3 -m unittest`, no cocotb) |
| `records/` | results ledger, **append-only** (see `records/README.md`) |

## What the suite checks

Every output byte is compared with `==` to `expected_out.hex` and to a live
`golden.gemm_int8` call; there is no tolerance. Each tile is loaded through the
Wishbone bank windows, run, and read back (serialized load-then-compute, valid
at every K up to 256; host/compute overlap is not exercised). The random run
takes its seed from `NPU_SEED` (drawn fresh if unset), prints it, and the
runner stores it in the record. Per-workload `U_array` (spec section 8), the
summed `PERF_CYCLES`, `ARRAY_N`, and the RTL commit go into the record,
labelled `simulated`; simulation uses the behavioral `npu_sram_bank`, not a
macro. No throughput figure is quoted from them (that needs the clock corner).

Both sizes run every workload; wall time on one core is about 30 s (N=8) and
55 s (N=4) for the whole suite.

## Gate-level run (pre-layout, functional, modelled SRAM)

Runs the same `test_bitexact` suite, unchanged, on the recorded synthesized
netlist `rtl/synth/records/20261027-sky130-hd/npu_top_synth.v` (decision 0005
hold registers included) at `ARRAY_N = 8`:

```sh
PDKV=~/.ciel/sky130A/libs.ref/sky130_fd_sc_hd/verilog    # pinned in flow/pdk.json
.venv/bin/python verification/runner.py --toplevel npu_top \
    --sources rtl/synth/records/20261027-sky130-hd/npu_top_synth.v \
              $PDKV/primitives.v $PDKV/sky130_fd_sc_hd.v \
              verification/models/sky130_sram_4kbyte_standin.v \
    --define FUNCTIONAL --define 'UNIT_DELAY=#0' --baked-param ARRAY_N=8
./verification/check_mutation_gl.sh      # negative control: must exit 0
```

What this is, and is not:

- **Pre-layout and functional.** Zero-delay `sky130_fd_sc_hd` functional models
  on the netlist as synthesized. No placement, no routing, no SDF.
- **The SRAM is modelled.** `verification/models/sky130_sram_4kbyte_standin.v` is
  a behavioural **stand-in, not the macro's view** (the 4 KB macro has no
  generated Verilog yet, #51). It follows the read timing recorded in
  `rtl/pdk/sky130/README.md` ("Read latency finding"): inputs sampled at the
  rising edge, `dout` driven after the falling edge, X after the next rising
  edge. Its only delay is a nominal 1 ns ordering delay, not a macro figure.
- **No timing claim.** Nothing here says anything about setup, hold, clock
  period or the macro's access time.
- `--baked-param` exports `ARRAY_N` to the tests and the record without passing
  `-P` to Icarus: the netlist has no parameters left.
- Do not add `rtl/pdk/sky130/npu_sram_bank_bb.v` to this source list; it declares
  the same macro module as a black box. The netlist already contains the bank
  wrapper.
- The record carries `defines`, `baked_parameters` and `source_sha256` (netlist,
  both PDK model files, the stand-in).
- Wall time on one core is tens of minutes (about 1,900 simulated ns per second).

Stand-in fidelity checks (Icarus, from the repo root):

```sh
# 1. The wrapper over the stand-in prints the same capture trace as the behavioural bank
iverilog -g2012 -o /tmp/b.vvp verification/models/tb_standin_1024.v rtl/pdk/sky130/npu_sram_bank.v && vvp /tmp/b.vvp > /tmp/b.txt
iverilog -g2012 -DNPU_SRAM_MACRO -o /tmp/m.vvp verification/models/tb_standin_1024.v \
    rtl/pdk/sky130/npu_sram_bank.v verification/models/sky130_sram_4kbyte_standin.v && vvp /tmp/m.vvp > /tmp/m.txt
diff /tmp/b.txt /tmp/m.txt && echo identical
# 2. Direct timing: X after the rising edge, valid after the falling edge, X again
iverilog -g2012 -o /tmp/t.vvp verification/models/tb_standin_timing.v \
    verification/models/sky130_sram_4kbyte_standin.v && vvp /tmp/t.vvp     # PASS standin timing
```

The bench samples `wb_dat_o` at the rising edge that ends the ACK cycle (where a
Wishbone master captures it), not at the falling edge: with a macro, the host
read data is only driven after the falling edge.

## PDK-independent files (stamped into `asap7-npu`)

All of them except `models/` and `check_mutation_gl.sh`: `runner.py`, `check_mutation.sh`, `requirements.txt`, `tests/`
(`npu_bench.py`, `test_bitexact.py`, `test_golden.py`), `golden/`, `workloads/`,
`records/README.md` and this README, plus `.github/workflows/verification.yml`.
Nothing here references sky130 or any PDK except the default seam value
(`rtl/pdk/sky130`).

## Pointing the harness at another layout

`rtl/check.sh`, `runner.py` and `check_mutation.sh` read two variables, so a
stamped port edits no script:

- `NPU_RTL_DIR` (default `rtl`): the 7 PDK-independent RTL files.
- `NPU_PDK_DIR` (default `rtl/pdk/sky130`): `npu_sram_bank.v` and
  `npu_sram_bank_bb.v`.

Relative values resolve against the repo root; absolute values are used as given.
The two directories need not be nested. `verification.yml` sets both in its
workflow-level `env:`, which is the one place a port changes.
`tests/test_relocated_layout.py` runs `rtl/check.sh` against a relocated copy.
