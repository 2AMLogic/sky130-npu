# verification

cocotb + Icarus harness and the bit-exact testbenches for `rtl/npu_top.v`,
compared byte for byte with the integer golden model (`golden/`).

## Cold start

Needs Python 3.9+ and Icarus Verilog 13.0 (CI builds tag `v13_0`; the runner
records the `iverilog -V` string in every record).

```sh
python3 -m venv .venv
.venv/bin/pip install -r verification/requirements.txt
.venv/bin/python verification/runner.py                    # ARRAY_N=8 (target)
.venv/bin/python verification/runner.py --param ARRAY_N=4   # fallback size
./verification/check_mutation.sh                            # suite must catch a 1-bit RTL error
```

Exits 0 and writes one record under `verification/records/` on success; exits
non-zero on any test failure (a failing run still writes its record). To
enforce the Icarus version: `EXPECT_ICARUS=13.0 .venv/bin/python verification/runner.py`.

The runner takes the DUT from arguments or env, so nothing needs editing in a
stamped copy:

```sh
.venv/bin/python verification/runner.py --toplevel mydut \
    --sources rtl/a.v rtl/b.v --param WIDTH=16 --test-module test_mydut
```

The defaults are `npu_top`, the `rtl/check.sh` source list, `ARRAY_N=8` and
`test_bitexact`. (`HDL_TOPLEVEL`, `HDL_SOURCES`, `HDL_PARAMS`, `TEST_MODULE`,
`TEST_DIR`, `RECORDS_DIR`, `BUILD_DIR`, `TESTCASE` (one test function),
`NPU_SEED` (random-test seed) are the env equivalents.) Parameters are also
exported to the test as environment variables.

## Layout

| Path | Role |
|---|---|
| `runner.py` | cocotb runner, Icarus, parameter-driven; writes the ledger record |
| `requirements.txt` | pinned cocotb |
| `tests/npu_bench.py` | Wishbone master, bank load/store, tiling, utilization accounting (touches only `npu_top` ports) |
| `tests/test_bitexact.py` | the four reference workloads, requantization edge vectors, K extremes, back-to-back, reset mid-run, `ERR_CODE` 1..5, constrained random |
| `check_mutation.sh` | corrupts one RTL output bit in a temp copy and passes only if the suite fails |
| `golden/` | bit-exact integer golden model and workload generator (spec sections 3, 4, 8) |
| `workloads/` | committed vectors for the four reference workloads, regenerated by `golden/workloads.py` |
| `tests/test_golden.py` | golden-model unit tests (`python3 -m unittest`, no cocotb) |
| `records/` | results ledger, **append-only** (see `records/README.md`) |

## What the suite checks

Every output byte is compared with `==` to `expected_out.hex` and to a live
`golden.gemm_int8` call; there is no tolerance. Each tile is loaded through the
Wishbone bank windows, run, and read back (serialized load-then-compute, valid
at every K up to 256; host/compute overlap is not exercised). The random run
takes its seed from `NPU_SEED` (drawn fresh if unset), prints it, and the
runner stores it in the record. Per-workload `U_array` (spec section 8), the
summed `PERF_CYCLES`, `ARRAY_N`, and the RTL commit go into the record,
labelled `simulated`; simulation uses the behavioral `npu_sram_bank`, not a
macro. No throughput figure is quoted from them (that needs the clock corner).

Both sizes run every workload; wall time on one core is about 30 s (N=8) and
55 s (N=4) for the whole suite.

## PDK-independent files (stamped into `asap7-npu`)

All of them: `runner.py`, `check_mutation.sh`, `requirements.txt`, `tests/`
(`npu_bench.py`, `test_bitexact.py`, `test_golden.py`), `golden/`, `workloads/`,
`records/README.md` and this README, plus `.github/workflows/verification.yml`.
Nothing here references sky130 or any PDK. The runner's default source list names
`rtl/pdk/sky130/npu_sram_bank.v`; a port points `--sources` at its own wrapper.
